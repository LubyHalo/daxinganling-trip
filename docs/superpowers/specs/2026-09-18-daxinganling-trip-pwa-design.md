# 大兴安岭 9 日自驾 · 离线旅行助手（PWA）设计

- 文档日期：2026-09-18
- 状态：待用户确认
- 行程：2026-09-19 ~ 2026-09-27（9 天，哈尔滨进出，舟山往返）
- 交付压力：**2026-09-19 10:00 舟山起飞**，v1 必须在 2026-09-18 夜间上线

---

## 1. 背景与约束

现状：工作区已有一份 `hulunbuir-7day-trip.html`（830 行单文件页面，旅行画册风格，逐日行程 + 住宿 + 小红书情报 + 贴士）。它是**纯静态只读页**：内容硬编码、依赖 Google Fonts CDN、无法在手机上修改或记手记。

新需求：一个手机上随时可查的旅行攻略，含路线、景点、住宿、美食；途中可自行调整；可写旅行手记。

用户已确认的前提（本次对话逐条确认）：

| 前提 | 结论 |
|---|---|
| 使用范围 | 我 + 同行的人，都要能打开同一份，一起补充 |
| 离线要求 | **硬要求**：草原/林区/边境线大量无信号，断网时必须能查能写 |
| 编辑深度 | 轻量：看 + 打卡 + 手记 + 小改（时间/备注/换店）；另需"跳过/推迟某景点"（仅本地）与"临时加自定义景点/餐厅" |
| 架构路线 | 本地优先 PWA |
| 后端 | **v1 不搭后端**：纯静态 + 手工同步码 |
| 照片 | v1 不做 |
| 视觉 | 双模式（路上速查 / 回酒店画册），v1 先做速查 |

---

## 2. 目标与非目标

**目标**

1. 无网络时可完整使用：查询行程、打卡、写手记、导出数据。
2. 多人各自在手机上补充，通过同步码交换数据，合并时不丢数据。
3. 行程骨架变更（换路线、增删天数）只需改数据文件，不改代码。
4. 现有页面的视觉资产可复用，不推倒重来。

**非目标（v1）**

- 照片、云端实时同步、账号体系、内嵌地图导航、完整行程骨架编辑、iOS/Android 原生 App。

## 3. 架构

三层，且**内容层与用户态层彻底分离**——这是整个设计成立的基础。

| 层 | 内容 | 存放位置 | 写入者 | 离线可用 |
|---|---|---|---|---|
| 内容层 | `trip.json`（行程、住宿、美食、情报、待办） | 构建时打包进应用，随 Service Worker 缓存 | 在电脑上维护，重新部署 | 完整 |
| 应用层 | 单页应用 + `sw.js` + 渲染逻辑 | 静态托管（HTTPS） | — | 完整 |
| 用户态层 | 打卡、手记、覆盖式小改、跳过/推迟、自定义点 | 手机 `localStorage` | 用户在手机上 | 完整 |

分离的意义：用户在手机上产生的手记/打卡**永远不会被内容更新覆盖**；同步只需交换很小的记录集合。此设计已在本项目上被验证过一次——行程骨架从「7 天海拉尔进出」整体换成「9 天哈尔滨进出」时，只需替换 `trip.json`。

**无网络请求**：应用主体不发起任何网络请求即可完整运行（除首次安装与检查新版本）。

## 4. 数据模型

### 4.1 内容层 `trip.json`

```jsonc
{
  "meta": {
    "id": "daxinganling-2026-09",
    "title": "大兴安岭 9 日自驾 · 穿越大兴安岭",
    "start": "2026-09-19",
    "end": "2026-09-27",
    "party": ["我", "同行人"],
    "flights": [
      { "date": "2026-09-19", "no": "FU6717", "from": "舟山", "to": "哈尔滨",
        "dep": "10:00", "arr": null, "price": 1420, "ticketed": true },
      { "date": "2026-09-27", "no": "FU6718", "from": "哈尔滨", "to": "舟山",
        "dep": "18:30", "arr": null, "price": 1680, "ticketed": true }
    ]
  },
  "days": [
    {
      "date": "2026-09-19",
      "n": 1,
      "title": "落地日 · 哈尔滨 → 齐齐哈尔",
      "route": ["哈尔滨", "齐齐哈尔"],
      "distanceKm": null,
      "stops": [
        { "id": "d1-s1", "name": "米家烤肉", "type": "food", "time": null,
          "note": "晚餐", "geo": null, "tips": null, "retired": false }
      ],
      "stay": { "name": "美希酒店（齐齐哈尔大商新玛特火车站店）", "phone": null,
                "addr": null, "booked": true, "links": [] },
      "intel": ["…"],
      "todos": ["办防火证"]
    }
  ],
  "tips": [ { "title": "温差与衣物", "text": "…" } ]
}
```

**稳定 id 规则**：`stop.id` 一经分配**永不改变**；下架景点用 `retired: true`，不删除节点。用户的覆盖与手记都挂在 `stop.id` 上，因此行程重排后手记不会错位。

### 4.2 用户态记录

```jsonc
{
  "id": "check:d1-s1",          // 见 4.3 确定性 id
  "kind": "check | note | override | status | custom",
  "trip_id": "daxinganling-2026-09",
  "target": "d1-s1",            // 挂载锚点；custom 为新建锚点 id
  "scope": "shared | local",
  "payload": { },
  "updated_at": 1758100000000,  // 毫秒时间戳
  "device_id": "dev-7f3a",
  "deleted": false,
  "deleted_at": null
}
```

### 4.3 确定性 id（手工同步能成立的关键）

| kind | id 规则 | 含义 |
|---|---|---|
| `check` | `check:<target>` | 打卡完成 |
| `override` | `ovr:<target>:<field>` | 覆盖某字段（如 `time`、`stay.name`） |
| `status` | `status:<target>` | 跳过 / 推迟（`payload: {value:"skipped"｜"deferred", to?:日期}`） |
| `note` | 随机 uuid | 手记是"新增事实"，每次都是新记录 |
| `custom` | 随机 uuid | 自定义景点/餐厅，`payload.day` 为日期锚点 |

同一件事（如"第一天第一站已打卡"）在所有人手机上算出**同一个 id**，合并时无需匹配，直接按 `updated_at` 取新。手工同步最容易出错的重复/错位问题由此消除。

### 4.4 scope 与默认值

| kind | 默认 scope | 说明 |
|---|---|---|
| `check` | shared | 同伴该知道进度 |
| `note` | shared | 一起补充的核心 |
| `override` | shared | 时间/备注/换店对同伴有效 |
| `status`（跳过/推迟） | **local** | 用户明确要求"只影响我自己" |
| `custom` | shared | 新增景点通常想让大家知道 |

界面上每条操作附一个"通知同伴"开关，可临时把 `local` 改成 `shared`。**`local` 记录永不进入导出数据**。

### 4.5 自定义点的锚点

用**日期字符串**（`2026-09-21`）而非"第 N 天"作为锚点：行程天数增删时，用户自加的餐厅不会跑错日子。渲染顺序按 `time`，无 `time` 时排在当天末尾。

## 5. 同步协议（无后端）

### 5.1 合并算法

```
导入对方数据 = 按 id 做并集；同 id 取 updated_at 更新的那份；软删除标记照常传播
```

### 5.2 铁律

1. **导入永不删除本地数据**。只有本机的删除动作才会删。因此"导入错文件"的最坏结果是什么都没发生。
2. **删除是软删除**（`deleted:true` + `deleted_at`），否则删除永远传不到别人手机上。
3. **字段级覆盖**：改集合时间只产生 `ovr:<target>:time`，不会冲掉同伴改的同一条备注。
4. **导入立即写回本地**（合并结果落盘），避免二次合并出现分叉。

### 5.3 交换格式与方式

- 主：导出 `.json` 文件（微信发送）
- 备：压缩后的**同步码文本**（gzip + base64，可直接粘贴到微信；记录少时很短）
- 导入：支持"粘贴文本"与"选择文件"两种

### 5.4 冲突

同 id 且同一字段两边都改过时，按 `updated_at` 取新，并在结果摘要中列出：「⚠ 1 处冲突已按较新时间采用」。v1 不做人工选择冲突。

### 5.5 使用节奏

每晚回酒店连 WiFi 对一次；汇总人可一次导入多份，再回发一份总码。

### 5.6 已知代价（明确接受）

- 非实时：改动要等下一次同步才扩散。
- 无云端备份：手机丢失/清缓存即数据丢失。缓解：应用内"已 N 天未备份"提醒 + 危险操作二次确认。
- 行程骨架变更仍由电脑端维护 `trip.json`（用户已确认接受）。

## 7. 视觉

- **速查模式（v1 默认）**：高对比、无纸纹、系统字体、信息密集、大字号——为车内强光与单手操作优化。
- **画册模式（v1.1）**：沿用现有纸纹 / 衬线 / 河流时间轴的画册风，供晚上翻看。同一份数据两种外衣。
- **字体**：v1 速查模式使用系统字体（PingFang / 微软雅黑），**彻底去掉 Google Fonts CDN 依赖**；画册模式的中文字体做子集化后自托管，避免脱网掉字。

## 8. 部署

- 形态：纯静态站点，HTTPS（Service Worker 的硬性要求，局域网 http 无法安装）。
- 候选：GitHub Pages（免费）/ Cloudflare Pages（免费、一条命令部署）/ 腾讯云 CloudBase 静态托管（国内最稳，需实名）。
- 切换成本：应用为纯静态，换托管方**不需要改代码**。
- **上线窗口**：必须在 2026-09-18 夜间完成首次部署，所有人当晚点开一次完成安装；之后离线可用。
- 兜底：若托管失败，退化为单文件 HTML + 每晚手动更新（数据仍在本地）。

### v1.2 天气（2026-09-18 当晚追加）

这是唯一需要联网的功能，所以设计目标不是"功能多"而是"**绝不拖累离线可用性**"：

- **数据源**：Open-Meteo 预报 API。选择理由：免注册无 key（用户不需要任何账号）、响应头 `Access-Control-Allow-Origin: *`（静态页面可直连）、中国境内可用。代价是不如国内商业气象服务精细，且中国境内小地名要靠外部地理编码。
- **坐标**：写在 `days[].geo`，用 Open-Meteo 地理编码与 OSM/Photon 两套数据源交叉验证（奇乾、莫尔道嘎、根河、满归互相印证；"恩和"在两套源里都有重名干扰，最终采用 OSM 的呼伦贝尔恩和乡 50.8206/119.9093）。
- **一次请求**：9 个地点用经纬度逗号批量查询，只发一个请求（URL 417 字节，缓存约 3KB）。
- **每天认领自己的地点**（关键正确性点）：API 对每个地点都返回全部 16 天，同一天会出现 9 次。早期实现是"后写覆盖"，会导致**九天全部显示最后一个地点（哈尔滨）的天气**；现改为按 `places[].date` 认领，`primary` 标记专属数据，非行程日期用先到地点兜底。
- **离线与失败**：抓取结果存 localStorage（含抓取时间）；超过 `STALE_HOURS=6` 或有行程日期缺失时，联网才自动刷新；断网、HTTP 错误、返回结构异常一律保留旧数据，只影响天气卡片，其它功能完全不受影响，界面始终标明"几小时前更新"。
- **提醒是阈值判断而非气象结论**：降水 ≥30/60%、风 ≥40km/h、最低温 ≤5/0°C 各自给一句出行提示，措辞明确指向"注意"而不是代替当地判断。
- **明确不做**：逐小时预报、雷达图、多模型对比、天气预警推送。

## 12. 决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| 载体 | 本地优先 PWA | 唯一同时满足"离线可写 + 多人共享 + 保留现有设计" |
| 后端 | v1 无后端，手工同步码 | 协作频率是"每天一次"而非秒级；零成本、零运维 |
| 内容/用户态分离 | 强制分层 | 内容更新不得覆盖用户手记；已验证过一次 |
| 确定性 id | 同事实同 id | 无后端合并的正确性基础 |
| scope 字段 | 跳过/推迟默认 local | 用户明确要求"只影响我自己" |
| 照片 | v1 不做 | 需对象存储与离线图片队列，成本高；相册与微信群已覆盖 |
| 数据库 | `localStorage` | 记录量小（千级以内），可读、易导出；IndexedDB 留待 v2 |
